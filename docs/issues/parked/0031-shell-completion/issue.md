# Problem

コマンド名・フラグ・enum の選択肢は定義されているが、シェルの入力補完に使う手段がない。作者が補完を別に記述すると定義とのずれが生じる。CLIの利用者に補完のためのシェル設定を何度も求めると、導入の手間が大きい。

外部コマンドを使わず、定義と同じ情報から補完候補を出せるようにする。設計は `design.md` に置く。

# Rules

- 0008の機械可読な定義を共通の情報源として使い、スキーマ解析を複製しない。
- 候補は補完のたびにCLI自身が定義から返す。定義を変更したりCLIを更新したりしても、補完ファイルの再配置を求めない。
- 補完取得でrunや副作用のあるsetupを実行しない。
- 初期範囲はサブコマンド・フラグ・enum。外部コマンドを使う動的候補は含めない。
- 補完ファイルの配置は利用者が明示的に実行したときだけ行う。通常の実行ではファイルを書かない。
- ユーザーのシェル設定ファイルを変更しない。必要な設定は表示して利用者に委ねる。
- シェル設定はhacksh製のCLI全体で一度だけ済むようにする。補完ファイルはCLIごとに分ける。

# Acceptance Criteria

- 採用したシェルでネストしたサブコマンド、値を取るフラグ、enumの補完を検証する。
- 空白やシェルの特殊文字を含む候補が適切に扱われる。
- hidden・alias・-- の後の候補の扱いを明示する。
- 定義を変更したCLIで、補完ファイルを置き直さずに新しい候補が出る。補完取得でrunが呼ばれない。
- 2つ目以降のhacksh製CLIは、シェル設定を追加せずに補完を導入できる。
- 使っている hacksh のバージョンが異なるCLIを併用しても、互いの補完を壊さない。

# Open Decisions

- 最初に対応するシェル（zsh/bash/fish）。
- 補完問い合わせの入出力形式と、hacksh のバージョン間での互換性の扱い。
- 補完ごとのCLI起動時間が許容範囲か。実測して判断する。
- 共通ディレクトリがシェル設定に入っているかの判定方法。
- 補完ファイルの削除手段を提供するか。
- lazyな定義0004や配列オプション0007を導入した際の情報取得範囲。

# 見送る項目

[拡張計画](README.md)で実施しない項目。AI エージェントが読んで正しく呼び出せる CLI の基盤には必須でないか、曖昧さを増やすものを見送った。再開する場合は、ここに残した設計メモを出発点として独立したフェーズに切り出す。

## 任意データの受け渡し

元はフェーズ1。

- `runCommand` に型付きの任意データを渡し、コンテキストの `data` で受け取れるようにする。指定したオブジェクトを実行中の親子で共有し、別の呼び出しには持ち越さない。

見送る理由: ライフサイクルやプラグインと組で意味を持つ。単独ではクロージャやモジュールのスコープで代替できる。

設計メモ: 任意データのジェネリックをコマンド定義と呼び出し側でどう一致させるかを型付きの利用例で確定する。データ未指定の既存コードに型引数を要求しない。データの型と同一性、呼び出し間の分離を検証する。

## サブコマンドの別名とデフォルト

元はフェーズ3。

- `commandAliases` を追加する。正規名と別名の重複・衝突を検出し、ヘルプとエラーでは正規名を使う。
- デフォルトのサブコマンドを追加する。案は既存の子のキーを指定する `default`。明示的な名前がない場合にだけ選択し、未知の名前をデフォルトへ流さない。

見送る理由: 別名は人間向けの省略記法であり、AI エージェントには正規名だけを示すほうが曖昧さが少ない。デフォルトのサブコマンドは、名前を誤ったときに明確なエラーではなく別の挙動になる余地を生み、親子の引数境界の仕様確定にも手間がかかる。

設計メモ: デフォルト指定時は親の `run` より子を優先する。親のオプションは親が消費し、親の `--help` は親の一覧を表示する。子へ渡す引数と passthrough の境界を例で確定してから実装する。正規名・別名・非表示・デフォルトの組み合わせ、親の値付きオプション、未知名、親の `run` の呼び出し回数、ヘルプの対象を検証する。

## 遅延読み込みと非同期定義

元はフェーズ4。

- 個々の `subCommands` の値を関数・Promise で遅延読み込みできるようにする。
- コマンド情報、`args`、`subCommands` 全体を関数・Promise で渡せるようにする。値を直接渡す既存の形式も維持する。

見送る理由: 多数のサブコマンドを持つ大規模 CLI の起動時間を削るための機能であり、複雑さに対して得るものが小さい。将来の追加で破壊的変更にならないよう、公開関数の同期・非同期契約は[フェーズ1](phase-1-public-api.md)で確定する。

設計メモ: 定義を解決する処理を設け、パーサへ未解決の値を渡さない。静的に検査できる条件は `defineCommand`、遅延した値に依存する条件は解決時に検査する。解決済みの値は1回の実行内で再利用する。親の一覧を出すために子を読み込む範囲、複数の同時実行でのキャッシュ、解決失敗のエラー型を確定する。選択しない子の不要な読み込みを避けること、実行内の解決回数、同時実行の分離、Promise の失敗、遅延スキーマでも維持される出力型を検証する。ルーティングとヘルプで別々に loader を呼ばない。

## ライフサイクルとプラグイン

元はフェーズ5。

- `setup` / `cleanup` を追加する。
- `definePlugin` を追加し、前処理・後処理を複数コマンドで共有できるようにする。

見送る理由: `run` 内の try/finally で代替できる。プラグインは利用者のエコシステムができてから設計するほうが適切。

設計メモ: 実行順序案は、引数検証、親から子の setup、選択したコマンドの run、子から親の cleanup。setup が成功した範囲を記録し、run や後続 setup が失敗しても対応する cleanup を行う。ヘルプ・バージョン表示だけの呼び出しでは実行しない。プラグインは同じライフサイクルに接続し、別のパーサや独自の終了処理を持たせない。コマンド固有フックとの順序、親からの継承、二重登録、元のエラーと cleanup のエラーの優先関係、任意データの型を確定する。通常終了・検証失敗・setup失敗・run失敗・cleanup失敗の順序と呼び出し回数を、同期・非同期、複数プラグイン、親子コマンド、同時実行を含めて検証する。

## 構造化された名前付きオプション

元はフェーズ6。初回リリースの計画でも明示的に対象外としている。

- 配列・オブジェクトを CLI で表す規則を設計する。
- 合意した規則を明示的な指定で有効にし、型・パース・ヘルプ・エラーを実装する。

見送る理由: 規則が未決定であり、元の計画でも仕様確定まで実装しないとしている。当面は利用者が `z.string().transform(JSON.parse)` などで対応できる。

設計メモ: 反復指定、区切り文字、JSON、キー付き指定のどれを採用するかは未決定。具体的な利用例を用意し、空値、エスケープ、繰り返し順序、要素の coercion、エラー位置を比較して仕様を確定する。カンマ分割や JSON 解釈を通常の文字列オプションへ暗黙に追加しない。

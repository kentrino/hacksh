# CLI フレームワークの拡張計画

初回リリースで対象外とした機能を、依存関係に沿って追加する。元の [cli-framework.md](cli-framework.md) は初回リリースの仕様として保存する。本書のチェック欄は実装の完了状態を表し、すべて未着手とする。

基準実装は `13111cf`、初回リリースの検証記録は [acceptance.md](../issues/cli-framework/acceptance.md)。現状の公開 API は `defineCommand`、`runCommand`、`runMain` とエラー型であり、ヘルプは無色、コマンド定義とサブコマンドは静的に解決する。

## 共通方針

- 既存 API の既定動作を維持する。新しい挙動はオプションや追加 API で選択する。
- zod 4 と zod/mini の両対応、`z.output` の型推論、ESM、Node 22.18 以上と Deno の npm 経由利用を維持する。
- 引数の解釈は既存の共通トークン処理に集約する。ヘルプ、ルーティング、検証で別々の走査規則を増やさない。
- 親はサブコマンドより前の引数だけを検証し、子を実行するときに親の `run` は呼ばない。未知オプションの保存順と `--` の境界を維持する。
- citty の構成や実装を参考にできる。ただし、上記の zitty 固有の仕様を優先する。コードを転載する場合はライセンス表示を保持する。
- 各フェーズは仕様・型・実装・テスト・README を揃えて独立にレビューする。公開 API 案はそのフェーズの着手時に確定し、変更理由を実行記録へ残す。
- 公開、リリース作成、外部スクリプトの移行は本計画に含めない。

## フェーズ一覧

| フェーズ | 目的                                                             | 依存                       |
| -------- | ---------------------------------------------------------------- | -------------------------- |
| 1        | 実行・パース・表示を利用者のコードから組み合わせられるようにする | 初回リリース               |
| 2        | 引数とヘルプの表現を拡張する                                     | 1                          |
| 3        | 静的なサブコマンドの選択方法を拡張する                           | 1。ヘルプの統合検証は2の後 |
| 4        | コマンド定義を非同期に解決する                                   | 3                          |
| 5        | 実行ライフサイクルとプラグインを追加する                         | 1・4                       |
| 6        | 配列・オブジェクトを取る名前付きオプションの仕様を決める         | 2。仕様確定後に実装        |

2と3は設計上独立だが、ヘルプと型定義の編集が重なる。既定では順番に実施し、並列化する場合はファイルの担当を分ける。

## フェーズ1: 公開 API と実行コンテキスト

- [ ] `runMain` に引数配列を注入できるようにする。省略時は従来どおり `process.argv.slice(2)` を使う。
- [ ] `runMain` のヘルプ表示を差し替えられるようにする。通常のヘルプと検証エラー時の usage に同じ仕組みを使い、既存の `onError` は既定のエラー表示全体を置き換える。
- [ ] `createMain(command, options)` を追加し、呼び出し時の引数配列を受け取れる関数を返す。
- [ ] `parseArgs(command, argv)` を公開する。案は、検証済み `args` を返し、失敗時に既存の検証エラーを投げる形。内部のトークン型を公開契約にしない。
- [ ] `renderUsage` と `showUsage` を公開する。文字列の生成と出力を分離し、後者は同じ生成処理を使う。
- [ ] `run` のコンテキストに `cmd` を追加する。実際に実行するコマンドと、補完済みのサブコマンド名を参照できるようにする。
- [ ] `runCommand` に型付きの任意データを渡し、コンテキストの `data` で受け取れるようにする。指定したオブジェクトを実行中の親子で共有し、別の呼び出しには持ち越さない。

着手時に、任意データのジェネリックをコマンド定義と呼び出し側でどう一致させるか、表示関数の引数・非同期対応・出力先を型付きの利用例で確定する。データ未指定の既存コードに型引数を要求しない。

受け入れ条件: 注入あり・なしの argv、ヘルプとエラーの出力先、非同期 `onError`、戻り値、データの型と同一性、呼び出し間の分離を検証する。パース・文字列生成 API は標準出力や `process.exit` に触れない。

## フェーズ2: 引数とヘルプの表現

- [ ] 可変長 positional を追加する。案は固定 positional の末尾に別の配列フィールドを指定する `variadic`。複数指定、途中への配置、サブコマンドとの併用は定義エラーにする。`--` 以降は引き続き passthrough とする。
- [ ] `z.enum` の選択肢をヘルプに表示する。ラッパー内も読み取り、任意の union や refine から選択肢を推測しない。
- [ ] positional の表示名を任意に指定できるようにする。
- [ ] 名前付きオプションの値の表示名を指定できるようにする。
- [ ] 否定フラグ専用の説明文を指定できるようにする。
- [ ] boolean の `--flag=false` と `--flag=true` を受け付ける。その他の文字列はエラーとし、非 boolean のフィールドへ真偽値変換を適用しない。
- [ ] `NO_COLOR` / `CI` が指定された環境で ANSI 色コードを出力しないことを保証する。現状は無色なので、着色機能を新設する必要はない。

表示用の指定は、スキーマのキーで型チェックする `defineCommand` のオプションにまとめる。スキーマ読み取り層には選択肢の取得を追加し、他の層から zod の内部構造を参照しない。

着手時に、可変長配列の未指定時の値と default/optional の関係、表示名とエラー表示の関係、`--no-flag=false` の扱いを確定する。案は未指定の可変長値を空配列として検証し、否定形式への値指定をエラーにする。

受け入れ条件: 固定引数との混在、空・複数要素、要素ごとの検証エラーと位置、extras/passthrough の順序を検証する。boolean の文字列指定は初回リリースからの意図的な変更として回帰テストを更新する。説明文・選択肢・表示名を zod と mini の双方で検証する。

## フェーズ3: 静的サブコマンドの拡張

- [ ] `hidden` を追加する。親の一覧から隠すが、名前による実行とそのコマンド自身のヘルプは利用可能にする。
- [ ] `commandAliases` を追加する。正規名と別名の重複・衝突を検出し、ヘルプとエラーでは正規名を使う。
- [ ] デフォルトのサブコマンドを追加する。案は既存の子のキーを指定する `default`。明示的な名前がない場合にだけ選択し、未知の名前をデフォルトへ流さない。

デフォルト指定時は親の `run` より子を優先する。親のオプションは親が消費し、親の `--help` は親の一覧を表示する。子へ渡す引数と passthrough の境界を例で確定してから実装する。固定・可変長 positional とサブコマンドの併用禁止を維持する。

受け入れ条件: 正規名・別名・非表示・デフォルトの組み合わせ、親の値付きオプション、未知名、親の `run` の呼び出し回数、ヘルプの対象を検証する。

## フェーズ4: 遅延読み込みと非同期定義

- [ ] 個々の `subCommands` の値を関数・Promise で遅延読み込みできるようにする。
- [ ] コマンド情報、`args`、`subCommands` 全体を関数・Promise で渡せるようにする。値を直接渡す既存の形式も維持する。

定義を解決する処理を設け、パーサへ未解決の値を渡さない。静的に検査できる条件は `defineCommand`、遅延した値に依存する条件は解決時に検査する。解決済みの値は1回の実行内で再利用する。

着手時に、親の一覧を出すために子を読み込む範囲、複数の同時実行でのキャッシュ、解決失敗のエラー型、フェーズ1の公開関数の同期・非同期契約を確定する。公開関数の戻り型を変更する場合は移行手順を示す。

受け入れ条件: 選択しない子の不要な読み込みを避けること、実行内の解決回数、同時実行の分離、Promise の失敗、遅延スキーマでも維持される出力型を検証する。ルーティングとヘルプで別々に loader を呼ばない。

## フェーズ5: ライフサイクルとプラグイン

- [ ] `setup` / `cleanup` を追加する。
- [ ] `definePlugin` を追加し、前処理・後処理を複数コマンドで共有できるようにする。

実行順序案は、引数検証、親から子の setup、選択したコマンドの run、子から親の cleanup。setup が成功した範囲を記録し、run や後続 setup が失敗しても対応する cleanup を行う。ヘルプ・バージョン表示だけの呼び出しでは実行しない。

プラグインは同じライフサイクルに接続する。着手時に、コマンド固有フックとの順序、親からの継承、二重登録、元のエラーと cleanup のエラーの優先関係、任意データの型を確定する。プラグインに別のパーサや独自の終了処理を持たせない。

受け入れ条件: 通常終了・検証失敗・setup失敗・run失敗・cleanup失敗の順序と呼び出し回数を検証する。同期・非同期の双方、複数プラグイン、親子コマンド、同時実行を含める。

## フェーズ6: 構造化された名前付きオプション

元の計画は配列・オブジェクトを値に持つ名前付きオプションも対象外としている。これは未チェック欄にはないが、取りこぼさないよう別フェーズにする。

- [ ] 配列・オブジェクトを CLI で表す規則を設計する。
- [ ] 合意した規則を明示的な指定で有効にし、型・パース・ヘルプ・エラーを実装する。

反復指定、区切り文字、JSON、キー付き指定のどれを採用するかは未決定。具体的な利用例を用意し、空値、エスケープ、繰り返し順序、要素の coercion、エラー位置を比較して仕様を確定する。カンマ分割や JSON 解釈を通常の文字列オプションへ暗黙に追加しない。この仕様確定までは実装を開始しない。

## 完了判定と実行記録

各フェーズで、関連要件の型・挙動テスト、`pnpm ready`、`pnpm test:packed` を実行する。公開型と tarball を確認し、Node の対応下限と Deno で新機能を実際に使うケースを追加する。テストの成功だけでなく、本書の受け入れ条件と対応付けて確認する。

実行時は `docs/issues/cli-framework-next/` に要件対応表と担当を記録する。本書の全文を各 issue や引き継ぎに複製せず、フェーズ・節・変更点を参照する。レビュー開始時の実装コミットを固定し、修正時は同じ担当へ差分と指摘を渡す。

元の未チェック21項目はフェーズ1〜5ですべて扱う。任意データの API とコンテキストはフェーズ1に統合し、機能の重複を避ける。追加の明示的対象外である構造化オプションはフェーズ6で扱う。
